2. 可直接载入的内置蓝图／测试入口，清晰的用例编号和固定位置；原生／预期参照，且代理已先确认入口可用、对照有效。
3. 每项只写必要操作、预期结果及需观察的路径；常规6—12项，不重复派发已通过的整表。
4. 结果表支持“通过／失败／未检查／阻塞”，记录截图、路径和复现条件；用户可只回复用例编号及差异。

未完成候选或原生对照无效的项目应提前标明“阻塞”，不让用户花时间重新搭场景，也不能将这部分登记为通过。已有静态蓝图可复用，但必须为本周版本说明实际入口和操作，不能仅发一个历史脚本路径。

- 10-24／25完成第一轮代表场景监督，10-31／11-01完成必要复测和最终人工验收；自动审计、必要冷启及最终来源核对通过。独立于变换的原有缺画／材质／动画问题继续归各自专项，不全部变成镜像算法的前置依赖；确由变换引起的数据、伙伴或显示错误仍阻塞镜像交付。特殊家族未取得有效观察的部分继续标为待验，不扩大已通过范围。

## 定期重构的目的、范围与验收

重构服务于后续开发效率和可靠性：共用规则分散、相同状态在三条显示路径重复处理、候选分支与生产来源混杂、测试工具重复搭夹具，都会扩大修复影响面，使同类问题反复定位。优先整理实际妨碍当前交付的耦合点，使规则可独立验证、多个方块能复用同一修复、变更影响范围可以明确判断。

- **每期安排约6小时**，在周期前段分成1—2个可独立回归的小批次。冻结前完成，冻结后只允许必要修复，不开展大规模模块搬迁。
- **每三期（约45天）一次架构复盘**，首次放在12-03周期：根据最近缺陷和修改成本决定下一批边界。若确需较大整理，可将该期重构增至约8小时，相应将实现容量减至22小时，总容量不增加。
- 每次先写实际痛点、受影响调用方、目标职责和行为不变量，再实施；沿用项目技能的架构／引用链分析与按范围review要求。
- 行为保持类重构与行为修复分别说明。复用已有失败用例和必要回归，核对保存格式、typed NBT、公开操作入口、显示及生命周期；不通过删除断言、放宽阈值或重写旧证据制造通过。
- 合并前说明消除了哪一处重复、耦合或来源歧义，并给出相关功能回归结果。代码变短、文件变多或测试数量增加本身不算收益。
- 原生渲染大改和整套管线重写不作为默认周期任务；应先有具体阻塞证据、可回退的小步方案和相应验收包。历史失败证据及冻结来源继续保留。

## 每周／每期汇报

周五移交记录：可用候选、测试入口、已准备与阻塞项、周末要看的差异。周末结束记录：用户通过／失败／未测、需要修正的具体编号。每期发布记录：实际可用能力、已关闭的原待办、未关闭范围、重构解决的维护障碍、实际开发工时与额度。

只有最终版本中达到关闭条件的内容才能写入发布说明。未通过项继续留在统一待办，并在下一个周期重排；连续两次周末仍卡住的同一问题，应复盘根因、测试有效性和实现方案，而非反复提交相同诊断产物作为进展。
