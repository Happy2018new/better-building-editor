# 建筑剪贴板分享与导入评估

评估日期：2026-09-21。下文保留阶段 50 的格式与 SDK 评估；阶段 52 已实现产品分享/导入入口，实际 MP2 格式和验证见文末。

## 结论

64×128×64 建筑可以序列化为剪贴板文本。文本长度主要取决于实际方块和材质的重复程度；最大尺寸并不意味着一定需要很长的分享码。厚 1 格空心外壳约 4,200 字符，重复楼层样例约 6,900 字符；满区随机材质则达到几十万至上百万字符。因此建议支持单串分享，同时为过长内容预留分段或文件传输方式。

网易 3.9 Windows 开发客户端实测，最长 1,646,505 个 ASCII 字符通过 `SetClipboardContent` 写入后，`GetClipboardContent` 完整读回，与原串完全一致。这是已验证的长度，**不是 SDK 最大容量声明**；文档未给出统一长度上限。Android/iOS、系统剪贴板策略以及微信/QQ等聊天软件的传输限制尚未实测。

## 编码与测量方法

利用现有 v2 数据：建筑名称、尺寸、非空气计数、材质表、按 16³ 保存的精确分块。均匀分块保存单个材质编号，其他分块已使用压缩的 16 位材质索引。去除未使用材质后，将紧凑 JSON 以 zlib level 6 压缩，再转 Base64；评估包格式为 `MP1:<Base64>:<CRC32>`。CRC32 只用于检测损坏，不用于鉴权或可信来源证明。

每个样例都解码为 Document，并检查全部方块及尺寸完全一致。测试不创建原生模型、不写世界、不修改建筑库。当前本地库 v3 的条目是分页索引，正式导出必须读取全部分块页并构造完整数据，不能只复制列表索引。

全部样例尺寸均为 64×128×64，共 524,288 格。样例使用合成方块标识符测量数据处理，不代表实际方块注册表或某份真实建筑的精确长度。重复楼层包含楼板、外墙、窗户、柱子；随机样例逐格选择材质。65,535 种材质是格式极限压力样例，不代表常见建筑。

## 游戏内实测

环境：网易 Windows 客户端 3.9.0.401155，内嵌 Python 2.7.13，独立 MCDK 世界。下表是单次计时；毫秒分辨率导致部分很短的编码操作记为 0，不表示没有开销。编码包含 JSON、已有分块编码、压缩和 Base64；解码包含解压、JSON 解析及草稿重建。样例生成、方块逐格核对、原生模型生成和 UI 动画不计入这些时间。

| 空区域 | 0 | 165 | <1 | <1 | 7 |
| 同材质实心体 | 524,288 | 525 | <1 | 2 | 1 |
| 厚 1 格空心外壳 | 39,944 | 4,173 | 28 | 118 | 1 |
| 重复楼层，5 种材质 | 96,560 | 6,929 | 36 | 145 | 1 |

七个样例的 SDK 写入均成功，读回长度及文本完全一致。测试保存并恢复了原剪贴板的各个可备份格式，包括图片格式；若无法完整备份，工具会跳过剪贴板写入，只测编码。该测试通过实例绑定的 MCDK 调用 SDK，剪贴板不用于调试通信。

宿主 Python 3.13 也完成相同规模测试：厚 1 格外壳 4,169 字符、重复楼层 6,925 字符、随机 256 种材质 935,701 字符。Python 版本的随机序列、JSON 顺序和压缩输出可造成长度差异。宿主耗时不能替代游戏或手机耗时。

## 推荐产品交互

1. 建筑库提供“复制分享码”，完整读取该配置后写入系统剪贴板，显示名称、尺寸及复制结果。
2. “从剪贴板导入”直接调用 `GetClipboardContent`，避免要求用户把巨量编码粘入原生输入框，也避开原生文本输入过滤。
3. 校验成功后先展示名称、尺寸、方块数量，确认后保存为新的本地草稿。导入不会直接放置世界方块；后续“应用到世界”继续走现有服务端鉴权。
4. 编码、解码及分块装载显示进度并分批执行，完成前不替换当前草稿。实测 118–723 ms 的整次解码足以打断动画，正式实现不应在一次按钮回调中完成全部工作。
5. 内容过长时提示字符数量，并提供分段复制/接收能力或后续文件方式。分段需要传输 ID、总段数、序号和完整校验，收到全部段后才允许导入；单段阈值应根据目标手机和分享软件测试决定。

正式解析器需要限制输入长度、解压后总长度、64×128×64 尺寸、材质表长度及分块数量，拒绝损坏、重复、越界和未知版本的数据。要在受限解压后再解析 JSON，并对每块执行现有精确长度/索引检查。评估工具只处理自己生成的数据，其直接解压逻辑不是可直接对外使用的导入器。

当前配置只保存方块标识及附加值，不含箱子物品、告示牌文本、生物或结构 NBT。分享不能增加现有草稿格式没有的信息；接收方缺少模组材质时，应在导入预览中明确提示。

## 阶段 52 已实现的产品格式

评估中的 MP1 没有作为产品格式发布；正式功能使用 MP2（分段 MPS2），不将 MP1 评估字符串当成兼容承诺。使用现有有序 begin/palette/chunk/end 数据包、逐行紧凑 JSON、流式 zlib 和 Base64，完整原文 CRC32 校验；分段另有建筑 ID、序号、总数和单段 CRC32。CRC32 用于传输完整性检查，不是身份签名。

解析限制为文本 8 MiB、解压原文 16 MiB、单记录 32 KiB、记录数 2048、最多 128 个分块；Receiver 继续验证材质表、方块数量、尺寸、索引和顺序。解压每次最多输出 32 KiB，Python 2 使用结束哨兵检查完整流，拒绝截断与尾随数据。没有 eval/pickle 或导入时的世界事件。

控制器按约 3 ms 时间片推进并限频报告进度；原生剪贴板调用、末尾 Base64 拼接和单条记录解析仍是同步调用，不能保证每一次迭代严格低于 3 ms。弹窗先完成入场再开始编解码；关闭取消后续回调。导入确认后写入独立分页配置，最后才提交建筑库索引，失败不会替换当前草稿或旧索引。取消期间写出的未引用分页可能留待同一新 ID 后续保存覆盖。

`verify_sharing_workflow.py` 在 PC/F11 用真实按钮验证当前最大草稿的完整复制、读取、确认和 Esc，使用内存存储替身；另验证已保存分页导出、损坏码拒绝、乱序重复分段及 524,288 格随机 16 材质完整重建（44 段）。分段 12,000 字符是产品默认值，不代表任何聊天软件的保证。测试修正为分帧调用 SDK，连续同帧读取曾返回空；SDK 异常时界面提供重试提示。

一次测试实例退出打断了旧工具的恢复流程，原剪贴板内容未能恢复。已将剪贴板恢复放入独立 finally，后续完整回归恢复测试开始时的剪贴板，即使游戏通道断开也执行清理。未记录用户剪贴板内容。
