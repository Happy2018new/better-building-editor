## 结论与来源边界

参考 Java 能减少高度、流向和 UV 的试错，但不能整套照搬。当前高度候选在规范化液体／空气样本上与 Java **1.12.2** 的旧算法一致；Java **1.16.5**、**1.21.1** 和 **1.21.11** 采用不同规则。Bedrock／网易究竟与哪个参考一致，必须用有区分力的原生输入确认。Java 版本号不自动指定对应 Bedrock 算法。

研究从 Mojang 官方 version manifest 下载四个版本的客户端，全部核验官方 SHA-1 和文件大小，并保存 SHA-256。1.16.5／1.21.1／1.21.11 同时核验官方名称映射。CFR 0.152 用于本地查看；高度分支及关键常数另用 JDK 22.0.1 的 `javap -c -p` 核对。部分反编译的 `tesselate` 局部声明不合法，未执行或复制反编译 Java 源码。

官方客户端、完整映射、class 和反编译结果只位于忽略目录 `.runtime/java-water-study-20261013`。仓库保存 [四版本来源清单](../tools/data/java_liquid_reference_sources_20261013.json)、独立表达的 [复算工具](../tools/study_java_liquid_reference.py) 和 [数值结果](../tools/data/java_liquid_reference_math_20261013.json)，不分发游戏源码或客户端。Java 游戏本体不是开源项目；[官方映射公告](https://www.minecraft.net/en-us/article/minecraft-snapshot-19w36a)明确映射发布不改变游戏代码／资源的既有限制，[EULA](https://www.minecraft.net/en-us/eula)另有 Mod 分发约定。

## 高度：先区分规则，不从截图拟合

以下深度0–7只表示非下落源水／低水的研究输入，高度为 `(8-depth)/9`。现代 Java 的流体 amount／falling 与 Bedrock `liquid_depth` 不作全状态等价假设。四角样本记为 C=目标、A/B=两个正交邻格、D=对角格；缺失样本均为空气，没有上方水。

| 输入 C/A/B/D | 当前候选＝Java1.12.2参考 | Java1.16.5参考 | Java1.21.1／1.21.11参考 |
| --- | --- | --- | --- |
| 源水／空气／空气／空气 | `44/63=.698413`，byte178 | `80/117=.683761`，byte174 | `20/27=.740741`，byte189 |
| depth3／空气／空气／空气 | `5/36=.138889`，byte35 | `5/36=.138889`，byte35 | `5/27=.185185`，byte47 |
| depth3／空气／空气／对角depth3 | `5/18=.277778`，byte71 | `5/18=.277778`，byte71 | `5/27=.185185`，byte47，对角被跳过 |
| 源水／正交depth3／空气／空气 | `31/42=.738095`，byte188 | `85/117=.726496`，byte185 | `85/117=.726496`，byte185 |

复算直接调用当前 `LiquidHeightRule`，再与独立有理数计算对照；现有候选只在这些规范化样本上匹配旧 Java，不能扩展为全部遮挡／两层语义相同。工具不把任何参考设为 NEMC 已接受规则。

最少两个新上下文即可区分这三种参考假说：

1. 目标 depth3，只在 NW 对角放同深度水，其余邻格及上方为空气。旧四格规则给目标 NW `5/18`，其余三角 `5/36`；现代条件对角规则给四角均 `5/27`。不涉及高水权重，能先独立识别采样机制。
2. 在识别机制后重新采集隔离源水 H，比较预声明的权重10／11。新计划保留旧 R13 H／L 原始失败及3px边界，不覆盖或重新拟合旧结果。

这些输入尚未在本时段实机运行。实际原生邻域、独立石块相机标定、恒定结构纹理和背景贡献须先冻结，再比较预测。已有 R13 H 量化误差最多 .339px，仍不足以单独解释旧失败；这里列出的新参考也不自动成为失败根因。

## 流向：不能只依赖水面四角

Java1.21.1／1.21.11 `FlowingFluid.getFlow`（官方行58–102）读取四个水平相邻流体的 own height；相邻位置为空、且方块不阻挡运动时，还读取该相邻位置**下方**的流体。其贡献为 `hC-(hBelow-8/9)`。同类流体或空流体参与，异类被排除；falling 附近实体面还影响三维流向。该函数读取快照即可计算渲染方向，研究不要求引入传播模拟。

一个无需拟合的反例：目标是隔离源水，四个水平邻格为空，仅北侧空气下方有源水。两种输入“有／无这格下方水”在当前候选中水面四角完全相同，角高梯度都为零；Java 参考却在有下方水时得到北向流动贡献 `8/9`，使用流水顶面。因此 `candidate_flow_uv` 的角高梯度并不覆盖 Java `getFlow` 的全部信息。

下一轮应先增加这个输入对照，再冻结目标版本的方向解析器。用于缺失投影的高度、流向与遮面上下文必须继续读取完整建筑快照，不因实际世界占用导致某格不绘制就删除其上下文。上／下、同层、两层与异类液体需要各自明确的输入合同。

## UV：可保留的结构与真正的差异

Java所查四版本的普通水侧面均使用流水纹理的半宽：规范化 `U=0..0.5`；顶边 `V=(1-h)/2`，底边 `V=.5`。旧版 getU/getV 参数以0–16计，现代以0–1计，不能直接把实参数字视作同一单位。这个结构与当前 NW 区域／底部固定裁切相近，支持保留该大结构；并不证明网易图集的 `quad`、`replicate`、像素边缘归属或运行时过滤完全相同。

Java流水顶面取 `atan2(flow.z,flow.x)-pi/2`，按 NW、SW、SE、NE 提交四顶点，绕纹理中心采样。将其化为文档 x/z 坐标、理想三角函数且未缩边的模板后，与当前 `top_uv` 相差固定四分之一圈：**当前方向 code 减64**才得到该参考模板。东向流的 NW 角，Java参考为 `(.75,.25)`，当前同code为 `(.25,.25)`。工具核对全部256角度×6个点，共1536对，记录误差；这是模板关系，**不是已确认网易方向错了90度**。游戏实际 Mth 近似、八位角量化、图集边界与过滤需要分开处理。

Java1.16.5／1.21.1 顶面额外向平均UV收缩，1.21.1 的比例由 `TextureAtlasSprite.uvShrinkRatio=4/atlasSize` 给出。1.21.11 的 `tesselate` 已不含这段显式收缩；其 `TextureAtlasSprite` 的 getU/getV 仍线性，构造多了 padding。这里只记录已核对的方法差异，不断言新版整个图集过滤等价，也不应将旧 Java 的 shrink 常数直接放进网易 shader。

四版本原版水纹与网易版也作了独立字节及解码像素比较：尺寸相同，但八组 still／flow 的 RGB和RGBA均不相同。Java1.16.5／1.21.1／1.21.11 PNG alpha均180，目标网易still240／flow255；Java1.12.2还使用预着色水纹。动画metadata都声明still帧时长2，flow为空animation对象，但Java默认值不能作为网易缺失字段的证据。具体指纹、尺寸、alpha范围及比较结果保存在来源JSON。这进一步说明应复用算法结构，继续使用目标版本资源和材质。

四角高并不定义双线性连续曲面。当前网格有固定两三角，Java也提交四顶点的面；非共面顶点的内部应按实际三角形重心坐标插值。后续离线 raster／UV oracle 必须核对实际索引与顶点顺序，不能用双线性内部值误判合法的三角网格。

## Bedrock 材质仍是独立适配项

参见 [网易资源与 shader 核查](LIQUID_BEDROCK_REFERENCE_STUDY_20261013.md)。该报告以安装的 NEMC3.9.0.401155 字节为准，区分原版资源声明、当前候选和实际原生观察。

- 原版 still PNG alpha240／flow PNG alpha255，与生成拷贝一致；贴图alpha并不等于 terrain 最终透明度。当前诊断 .45 是覆盖值，不是原生透明度已被识别。
- 原版骨骼资源材质声明 Point 过滤，不应把跨帧 bilinear 混色写成当前已确认故障。图集边缘及实际活动材质仍需独立确认。
- TIME声明每210秒回绕；当前动画公式在回绕前相位分别趋向still第20帧／flow第8帧，归零后从第0帧开始，周期不整除。该算术风险可离线证明，实际原生动画节奏尚未接受。
- 固定透明面顺序、双面绘制与深度写入可影响多面叠加；Java的顶点／材质代码不能直接替换网易骨骼、UI和世界渲染路径。

## 下一轮实施和验收顺序

先完成纯离线规则、顶点／索引、四面方向、低水裁切、UV单位、编码、原版资源指纹、动画回绕和 owner 生命周期检查；让失败具有具体归属。规则依赖和资源依赖分别版本化，不用一套“大水渲染器”混合规则、SDK与测量代码。

随后在一个受管后台实例、已验证的 foot+2 位置集中验收。R11的重复静态帧已经实施，R12同图集立方体也已失败，不能把这些旧实验重新说成新方案。新的结构标记应是有明确方向和不同角特征的大块非对称纹理，用于几何／四侧／裁切；它不能单独证明精确采样器、每texel过滤、alpha或动画。

尽量控制为结构标记和正常资源两个冷资源阶段，复用同一受管实例配置；若原生缓存要求重启，则准确回收上一实例后再冷启动，不假定资源热更新有效。R11／R12的LOW/HIGH端点仿射RGB与四邻像素组合同时包含光度传递假说，连不透明同图集立方体也失败，无法把公共误差唯一归为水的透明叠面。结构marker应避开这项混杂，并继续保存原精确RGB诊断的失败。

原始 R11 RGB RMSE<=3、原 R13边界3px及全部失败保持原样。结构标记独立回答结构问题，原纹理回答产品画面问题；不以不透明标记通过关闭原纹理透明表现。恢复原纹理后分别完成内置蓝图编辑器、完整投影、缺失投影，覆盖含水本体／后方块可见、占用单格消隐、切面、旋转镜像、流动顶面和时间变化。沿用已接受14群系近似，不追求用户未要求的全部群系精确颜色。

模块建议在已有边界内落实：`liquid_shape`维护纯邻域计算；版本profile提供目标／正交／对角的采样策略、高度、流向和遮面策略；`liquid_face_textures`维护面资源和模板；生成器维护纹理／材质来源；`liquid_transport`维护编码；Scene／projection owner只负责提交、显示和释放。现代条件对角规则不能仅修改当前16项height／weight数据表达，因为现有四样本接口没有目标角色策略；若原生证据需要，给该边界增加显式策略，不重构全仓库。

动画修正不应为了整除210秒而擅自改变帧时长。应先核实能否使用现有原生动画／相位通道；否则设计由owner持有的连续相位输入，使几何缓存和动画更新分离，并保持UI／world各自生命周期及共同时间合同。当前四个vec4已经承载地址／面／方向、八对角高及外观，新增相位不能偷偷复用已有字段；必须经过版本化payload／shader共同变更及精度、恢复、暂停与长时间边界检查。本研究未确认新的SDK相位接口或实现此方案。

未来大版本适配先 diff 方块表、上述原版资源及规则profile，再重新生成变化的合同并运行这些判别上下文及三路径集中验收。Java参考用于查清算法与版本变化；网易实证决定启用哪一套，不能承诺引擎行为变化后完全免实机维护。
